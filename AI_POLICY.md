# AI Policy 
This documents the AI policy for the Braidpool, and every PR created in the codebase should follow the guidelines listed here. This policy doesn't mean to restrict the use of AI but allows the way to use AI efficiently and in the best possible manner. Previously we have seen the burst of PRs in the codebase, and many of them are generated by autonomous AI agents. The code written by autonomous models lacks accountability and code maintainability. New contributors are welcome and encouraged to use the AI to get a better and efficient view of the project.

#### A user is allowed to use AI if:

- They can explain the reasoning behind the logic they chose and can argue about their decisions.
- They must understand the purpose, behavior, design decisions and implications of the code they submit, and be able to explain the relevant implementation during review. 
- The code is first manually reviewed before pushing.
- The user uses a second, independent AI session to critically/adversarially review their PR before submission. This is the most useful way to iterate with AI: feed comments from the review back to the main session and iterate. But you still need to be able to explain to the maintainers what it created.
- It's better if comments are manually written by the PR author, although in certain cases using the AI for writing the comments is permissible, but they should reflect the true nature of the code and be manually verified. Failing to do this comes under the case of using the autonomous agents.

#### A user is not allowed to use AI for:

- Writing the PR description, title, commit name, and message.
- Using in discussion with maintainers and contributors. This includes sending the AI-generated comments, but one can reference a text that is written using AI only if it's previously disclosed.
- Using autonomous AI agents, meaning contributions made without a human in the loop who understands and takes responsibility for the resulting work.
- Using AI agents as co-authors or committers of a PR.
- Writing documentation.
- Creating a PR that lacks things described above in the allowed section.

The things described above will benefit every community member, contributor, reviewer, and maintainer. And will lead to a more strategic development process. **Any PR that is seen violating the above terms and suspected by the maintainers will be closed without giving a detailed reason or any reason for closure.**
